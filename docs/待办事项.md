## 架构决策待想清楚：两套记忆系统是否要合一

**现状（2026-08-27 查证）**：本地记忆和 EverOS 记忆**并行跑，每次对话两套都注入**——生产日志 35 次对话生成里，两个记忆段各出现 35 次，不是二选一。

两者的检索机制完全不同：

| | 本地记忆（Convex） | EverOS 记忆 |
|---|---|---|
| 怎么检索 | 我们算 embedding 向量，`ctx.vectorSearch('memoryEmbeddings', ...)` 库内比对 | 发**明文** query 过去（`method: 'hybrid'`），它自己在服务端检索 |
| 用不用我们的 embedding 模型 | **用**（`fetchEmbedding` 写入时算、`embeddingsCache.fetch` 查询时算） | **不用**，embedding 发生在它那头，算 MemCell 额度 |
| 内容长度 | 短，最长约 420 字 | 长篇叙事，p90 938 字 |
| 失败模式 | 数据库内操作，基本不会失败 | 外部 HTTP，8 秒超时，fail-soft 会**静默返回空** |
| 作用域 | 跟着 world 走 | 跨 world（v1.1 已加 `EVEROS_SCOPE_PREFIX` 隔离 dev/prod） |

**关键事实：EverOS 自带检索，不需要我们的 embedding 模型。** 所以如果哪天退掉本地这套，`LLM_EMBEDDING_MODEL` / `fetchEmbedding` / `memoryEmbeddings` 表可以整个拿掉，少一个模型依赖。

**但现在不建议动**，两者失败模式互补：本地是库内查询、基本不会挂；EverOS 是外部调用，网络抖一下就静默返回空。留着本地这层，等于 EverOS 挂了角色也不会突然失忆。

**真要简化，需要先回答的问题**：
- EverOS 单独扛得住吗？连续观察它的可用率和延迟，静默返回空的频率有多高
- 两套记忆的内容是否大量重叠？如果 EverOS 已经覆盖了本地那几条，本地就是纯冗余；如果各有各的角度，合并会丢信息
- 成本对比：本地是 AstraFlow 的 embedding 调用（每写一条记忆 1 次 + 每轮对话 1 次带缓存），EverOS 是 MemCell 额度，哪个更省要按真实用量算

这是个架构取舍（省一个供应商依赖 vs 少一层兜底），不是顺手能改的，值得单独一次讨论。

## v1.1 终审判为「部署后再说」的延后项

按价值排序。都不影响线上运行，随时可做。

**值得做**

- `sanitizeForPrompt` 的截断仍按 UTF-16 切，压中 emoji 边界会产出孤立代理（`convex/util/sanitize.ts:16`）。同一个 bug 在 UI 层（`SpeechBubble.tsx`）已经用 `[...text]` 按 code point 修好了，**这一层没修，两处不一致**。改法照搬 SpeechBubble。
- `generateRecap` 的 JSON 解析没有独立单测（`convex/director.ts`）。安全性目前靠外层 try 兜住，与已有 9 条测试覆盖的 `parseDirectorOutput` 同构但无回归保护。建议抽出 `parseRecapOutput` 纯函数再补测试。
- 章回体回目序号是 LLM 自编的，没有持久计数器，多条回顾之间序号不连贯（可能"第八十三回"后面跟"第十七回"）。不影响排序（`listRecaps` 按 `day` 排），纯观感。修法：prompt 里注入"这是第 N 回，N = 该 world 已有 recap 数 + 1"，或去掉数字只留标题。
- director 子系统的 catch 一律用 `console.log`（`director.ts:97, 213`；`conversation.ts:245`），而 `everosMemoryPrompt` 用 `console.error`。生产上判断"编剧是不是在静默跳过"全靠日志，`log` 级别不进多数平台的 error 告警。

**记着就行，当前无触发路径**

- 关系面板的去重键用中文名而非 `playerId`，未来若有重名访客会被误合并成同一个交往对象。
- `playerDescriptions` 的 `.collect()` 无上限（`convex/world.ts`，v1.1 新增）。该表每访客一行且 vacuum 永不清理，Convex 单次查询有约 1.6 万文档的硬上限，越过后 `playerMemories` 会**抛错而非降级**，角色面板整个挂掉。9 个 AI 角色 + 零星访客不构成风险，**但做推广活动前应改成按 playerIds 逐个 `.get()`**。
- `recentTitles` 去重窗口是 `take(3)`，只按标题去重，识别不了"换个标题还是同一个设定"。低流量下这个窗口可能横跨好几天。**如果发现事件题材单调，先看这里，别先调 temperature。**
- `day` 字段用 UTC 日期，与 cron 的 `hourUTC:15` 隐式耦合（15:00 UTC = 北京 23:00，当前日历日对齐）。**若单独改 cron 时间到北京跨日的时段，day 标签会错位一天。**
- 反思路径（`memory.ts` 的 `reflectOnMemories`）从未被真实触发过——需单角色累计 importance > 500（约 80+ 次对话）。它的失败模式**不是**静默跳过：`chatCompletion` 在 try 之外、`agentRememberConversation` 无 try，失败会让该角色悬挂到 `ACTION_TIMEOUT`（120 秒）才自愈。观察信号是日志里的 `Timing out {"name":"agentRememberConversation"...}`。
- `convex/util/llm.ts:157` 的 `console.log(body)` 会把完整 system prompt 打进日志。加上 EverOS 的 5×1000 字符注入后日志体量显著变大，留意 Convex 日志配额。
- `relationship` 类型的记忆**没有任何代码生成**（只有 schema 定义）。关系面板现在用 `conversation` 类型顶替。若将来真实现了该类型，需重新评估去重键和数据源。详见 PIT-0012。
- 未配 `eslint-plugin-react-hooks`。v1.1 的 hook 顺序是人工核实的，下一个改 `Player.tsx` 的人没有护栏。
